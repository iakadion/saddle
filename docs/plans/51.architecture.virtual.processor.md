# Arquitetura V3 - Repo como Processador Virtual

## 1. GitHub Actions como FaaS (Function as a Service)

Cada workflow é uma função:

```yaml
on:
  workflow_dispatch:
    inputs:
      job_id: string
      binary_url: string
```

Browser chama via API, Action executa, commita resultado.

ToS diz que não pode usar como serverless puro, mas para processamento de binário do próprio repo é uso válido.

## 2. Storage como RAM - Técnicas

### Swap File
```bash
fallocate -l 16G /mnt/swapfile
mkswap /mnt/swapfile
swapon /mnt/swapfile
# Agora você tem 16GB RAM virtual vindo do disco
```

### tmpfs RAM Disk
```bash
mount -t tmpfs -o size=8G tmpfs /mnt/ramdisk
# /mnt/ramdisk é RAM, mas parece disco. 10x mais rápido que SSD.
```

### /dev/shm
Já é tmpfs por padrão, 50% da RAM. Use como workspace.

### ZRAM
Comprime RAM em tempo real, 2-3x mais capacidade.

## 3. Multi-Repo Farm para Ilimitado

GitHub Free: 500MB artifacts por conta, 10GB cache por repo.

Solução: sharding

```
Controller repo (opencode-main)
  -> dispara via API para
    opencode-worker-1 (500MB)
    opencode-worker-2 (500MB)
    ...
    opencode-worker-100 (500MB) = 50GB
```

Cada worker é repo público idêntico. Controller faz round-robin.

Mesma ideia para Codeberg (750MB soft), GitLab (10GB por projeto).

## 4. Multi-Forja

- GitHub: principal, minutos ilimitados público
- Forgejo: self-hosted na sua VPS, 100% ilimitado, compatível 95% com GitHub Actions
- Gitea: similar Forgejo, usa .gitea/workflows/
- Codeberg: Forgejo hospedado, Woodpecker CI, sem limite para FLOSS
- GitLab: 400 min, 10GB storage, mas Pages de 100MB e Registry separado

Você pode fazer mirror push para todas as forjas simultaneamente e ter 4x compute.
