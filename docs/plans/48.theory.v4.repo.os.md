# V4 - Teoria Completa: Repo como Casa do OS

## Fatos que você trouxe - raciocinando junto

### Fato 1: No Linux tudo é arquivo
> Everything is a file - open/read/write/close retornam file descriptor

No kernel tudo é struct inode + dentry + file_operations. Processo, memória, device, socket - tudo é arquivo.

```c
struct file_operations {
  .read, .write, .mmap, .open...
}
```

Se implementa file_operations, É arquivo. VFS (Virtual File System Switch) abstrai ext4, tmpfs, proc, sysfs.

Prova que storage e RAM são mesma coisa: ambas são files com backing diferente.

### Fato 2: Formatos, mimetypes, magic bytes
Extensão é UX. Verdade está nos primeiros bytes:

```
ELF: 7F 45 4C 46
PE: 4D 5A (MZ) + 50 45 00 00 (PE)
PNG: 89 50 4E 47 0D 0A 1A 0A
ZIP: 50 4B 03 04 (por isso DOCX, APK, JAR = ZIP)
```

`file` usa libmagic para detectar. MIME type é pra web (Content-Type), magic byte é pra SO decodificar.

Repo guarda esses bytes estáticos. Quando busca, decodifica via magic.

### Fato 3: Encoding e Decoding
Todo arquivo estático precisa encode/decode:

- Encode: arquivo no disco (bytes estáticos)
- Decode: loader lê magic, escolhe parser, mapeia pra RAM, executa

Ex: Windows instala, arquivos ficam estáticos. Na hora de rodar, busca paginação, dump de memória, decodifica PE -> mapeia seções -> executa.

Mesma coisa no nosso caso: repo guarda binário estático com magic, browser faz fetch, decodifica via WASM loader, executa.

### Fato 4: Sandbox tem VFS e virtual file - Docker, K8s

Docker usa OverlayFS:

```
lowerdir=/lower1:/lower2 (read-only, camadas da imagem)
upperdir=/upper (writable)
merged=/merged (o que processo vê)
copy_up: primeira escrita copia arquivo inteiro do lower pro upper
```

Imagem OCI = stack de tar.gz estáticos. `docker run` = monta overlay + cria namespace.

Kubernetes ephemeral storage = tmpfs + emptyDir que é RAM.

Ou seja: arquivos estáticos viram sistema rodando via overlay.

### Fato 5: Virtual file e virtual RAM, VMs

VM = arquivo estático (qcow2, vmdk) + emulador que decodifica e executa.

v86: boota Linux no browser de arquivos estáticos:

```js
new V86({
  bios: {url: "./bios/seabios.bin"},
  cdrom: {url: "./images/linux.iso"} // ISO estático no GitHub Pages
})
```

WebContainers: Node compilado pra WASM, FS em SharedArrayBuffer, roda npm de arquivos estáticos.

### Conclusão dos fatos

> Local pra guardar arquivos com decode/encode pronto já temos ilimitado: GitHub, GitLab, Forgejo, Codeberg, etc. Casa onde OS vai ser alocado já tem. Precisa fazer ele rodar como emulador/VM.

Arquivos estáticos no repo = /usr, /bin, /lib do OS
Gatilho = bootloader que busca e decodifica
Site estático = BIOS que conversa via HTTPS
Actions = CPU que processa paginação

### Transformação Storage <-> Compute nos dois sentidos

**Storage (repo) -> Compute (RAM):**
- `mount -t tmpfs -o size=8G tmpfs /mnt/ramdisk` -> RAM vira disco
- `fallocate + mkswap + swapon` -> disco vira RAM
- `git clone --separate-git-dir=/dev/shm/repo.git` -> .git em RAM pura
- `mount -o bind /dev/shm/repo /mnt/repo` -> repo em RAM

**Compute (RAM) -> Storage (repo):**
- Processa em /mnt/ramdisk
- `git add docs/results/ && git commit && git push` -> RAM virou storage persistente
- `upload-artifact` -> RAM virou artifact
- Release asset -> RAM virou CDN

Diferença entre 10GB RAM e 600GB storage é só flag: um é tmpfs, outro é ext4, mas ambos são inode no VFS.

### Infra de Bridges e Escadas (gatilhos)

Você falou que precisa de gatilho pra ficar acionando repo toda hora. Exato:

```
Site A (Pages) --fetch POST--> api.github.com/dispatches --trigger--> Action Worker
Action --commit docs/queue.json --> Pages rebuild --> Site B lê via GET

Site A e Site B são estáticos, mas conversam via HTTPS como se fossem processos via pipe.
```

Gatilhos:
- repository_dispatch: cross-repo, precisa PAT, 0 custo disparo
- workflow_dispatch: retorna run_id pra polling
- workflow_call: reusable
- workflow_run: chain intra-repo

Cada arquivo estático no repo vira handler:

- /api/handler.json -> endpoint
- /api/queue.json -> fila de mensagens
- /dumps/incoming/ -> inbox de binários

Outro sandbox chama via fetch, dispara Action, Action processa e commita resultado.

### V4 Arquitetura Final

```
[Browser - index.html 50KB estático no Pages]
  - VFS virtual em JS: mapeia magic bytes -> decoder
  - Preview 256 bytes via File API slice (não pesa)
  - Gatilho: fetch dispatch

[Bridge Layer - GitHub API como barramento]
  - repository_dispatch como IPC
  - Pages JSON como shared memory

[Compute Layer - Actions Farm]
  - Cada Action = CPU que boota de arquivos estáticos do repo
  - OverlayFS: lowerdir = repo (read-only), upperdir = /mnt/ramdisk (writable)
  - Storage transformado em RAM via swap + tmpfs
  - Resultado commitado de volta pro repo

[Storage Layer - Repo como disco infinito]
  - docs/results/ = paginação persistente
  - releases/ = .iso, binários grandes
  - docs/api/ = handlers estáticos
```

Tudo é arquivo. Repo é disco. Action é CPU. Pages é barramento. Site estático é BIOS.

É um OS distribuído em cima de Git.
