## Sumário Executivo

`@wenathlan/webscrape` é um toolkit de scraping all-in-one que ocupa um nicho único: combina HTTP scraping, browser automation, serialização multi-formato, formatação para IA e um servidor HTTP — tudo em um único pacote TypeScript, sem depender de serviços em nuvem. A análise técnica revela que, enquanto competitors como Crawlee e Scrapy dominam em infraestrutura de produção (filas persistentes, Docker, anti-detection), webscrape supera em integração com IA, estimativa de tokens e chunking para RAG.

## 2. Comparativo de Arquitetura

### 2.1 Crawlee: Request Queue vs Nossa Batch

**Crawlee — Request Queue (Persistent):**
```
User Code
  → Request Queue (SQLite/disk/cloud)
    → Request Handler
      → Storage (Dataset + KV Store)
        → Local filesystem OR Apify Cloud
```
- Queue sobrevive a restarts
- Handle milhões de URLs
- FIFO/LIFO ordering
- Dedup persistente (URLs já processadas)
- Auto-scaling baseado em recursos do sistema

**webscrape — Batch Processing (In-Memory):**
```
batchScrape(urls, options)
  → p-limit (concurrency control)
    → scrapeUrl() per URL
      → results[] + errors[]
```
- Queue é um `Array` em memória
- Sem persistência entre execuções
- Dedup via `Set<string>` no crawler (também in-memory)
- Sem auto-scaling
- Suporta parallel e sequential modes

**Análise:** O gap é significativo para uso em produção. Para crawling de grande escala (>10k URLs), a falta de queue persistente é bloqueante. Para uso típico de scraping (100-500 URLs), o batch approach é suficiente e mais simples.

### 2.2 Playwright Integration Patterns

**Playwright (raw):**
```typescript
const browser = await chromium.launch();
const context = await browser.newContext();
const page = await context.newPage();
// Auto-wait, locators, tracing, mobile emulation
```

**webscrape (wrapper):**
```typescript
const browser = createBrowser({ headless: true, blockAds: true });
await browser.launch('chromium');
// Simplified: navigate, click, type, screenshot, scrollToBottom
// Mas sem: auto-wait, locators, tracing, mobile profiles
```

**Crawlee (crawler pattern):**
```typescript
const crawler = new PlaywrightCrawler({
  requestHandler: async ({ page, request }) => {
    // Full Playwright API + built-in retry, session, proxy
  },
});
await crawler.run(['url1', 'url2']);
```

**Análise:** O wrapper de webscrape simplifica Playwright para casos de uso comuns, mas perde recursos avançados como auto-wait (elimina timeouts flaky) e locators (element finding resiliente). O pattern do Crawlee é mais maduro para crawling, mas mais verboso para scripting simples.

### 2.3 Abordagens de Serialização

**webscrape (5 formatos):**
```typescript
serializeResult(result, { format: 'markdown' }) // Custom JSDOM serializer
serializeResult(result, { format: 'xml' })       // JSDOM → XML
serializeResult(result, { format: 'json' })      // Structured JSON
serializeResult(result, { format: 'redis' })     // JSON.SET command
serializeResult(result, { format: 'text' })      // Strip tags
```
- Implementação customizada (não usa Turndown)
- Markdown serializer processa: h1-h6, p, br, hr, ul/ol, a, img, strong, em, code, pre, blockquote, table
- Redis output gera comando `JSON.SET` pronto para executar
- Suporta chunking por tamanho máximo

**Scrapy (Feed Exports):**
```python
FEED_FORMAT = 'json'
FEED_URI = 'output.json'
# + CSV, XML, automatic database export
```

**Firecrawl (API-native):**
```json
{ "formats": ["markdown", "html", "rawHtml", "screenshot"] }
```
- Markdown via Turndown com GFM
- Screenshot como feature nativa
- Structured output com Zod schemas

**Análise:** A serialização do webscrape é surpreendentemente robusta, com suporte a Redis (único na lista) e XML customizado. O gap está na qualidade do Markdown — Turndown (usado por Firecrawl) lida melhor com edge cases (nested lists, complex tables, inline HTML).

## 3. O Que os Concorrentes Fazem Melhor

### 3.1 Anti-Detection (CRÍTICO)

**Cenário atual:**
- `headers.ts`: 4 profiles (Chrome/Firefox/Safari) — User-Agent rotation básica
- `browser.ts`: `'--disable-web-security'` hardcoded (risco de segurança)
- `puppeteer-extra-plugin-stealth` está em `optionalDependencies` mas NÃO é utilizado

**O que falta:**
| Capacidade | Implementado | Concorrente |
|-----------|-------------|-------------|
| Fingerprint randomization | ❌ | Crawlee: human-like fingerprints automáticos |
| TLS fingerprint | ❌ | Browserless: TLS fingerprint rotation |
| Canvas/WebGL spoofing | ❌ | Firecrawl: stealth mode com proxy residential |
| Navigator properties | ❌ | Browserless: BrowserQL custom detection bypass |
| Captcha solving | ❌ | Firecrawl: captcha handling integrado |
| Proxy residential | ❌ | Firecrawl/Browserless: IP rotation gerenciada |

### 3.2 Filas Persistentes (ALTO)

**Impacto:** Impossível resumir crawls após crash, impossível lidar com milhões de URLs.

**Crawlee oferece:**
- `RequestQueue` com SQLite local ou cloud storage
- Dedup persistente (URLs processadas sobrevivem a restarts)
- Priorização de requests
- Auto-skip de URLs já processadas

**webscrape tem:**
- `Set<string>` in-memory para visited tracking
- `Array` como queue (BFS)
- Sem persistência

### 3.3 Docker (ALTO)

**Todos os competitors oferecem:**
- Crawlee: templates `Dockerfile` + `docker-compose.yml`
- Browserless: Docker-first architecture
- Firecrawl: self-hosted Docker deployment
- Scrapy: Scrapyd para deploy como serviço

**webscrape:** Sem Dockerfile, sem container deployment, sem Kubernetes support.

### 3.4 MCP Server (MÉDIO-ALTO)

**Competitors com MCP:**
- Playwright: `@playwright/mcp` — browser automation para AI agents
- Firecrawl: `firecrawl-mcp` — scrape/crawl como MCP tools
- Browserless: MCP server integrado
- Puppeteer: `chrome-devtools-mcp`

**webscrape:** Sem integração MCP — não pode ser usado por Claude Desktop, Cursor, Windsurf nativamente.

### 3.5 Sessions Persistentes (MÉDIO)

**Browserless:** 90 dias de retenção de cookies/cache/localStorage
**Crawlee:** Persiste sessões em disco
**webscrape:** `CookieJar` e `ScrapingSession` são in-memory — perdem estado entre execuções

## 4. O Que Nós Fazemos Melhor

### 4.1 Cross-Runtime (ÚNICO)

```
Node.js >= 26.2.0 ✅
Bun >= 1.4.0      ✅
```

Nenhum outro competitor suporta Bun nativamente. Crawlee e Puppeteer são Node-only. Playwright tem suporte multi-language (Python, Java, .NET) mas não Bun. Isso abre oportunidades para edge runtimes e performance superior em Bun.

### 4.2 All-in-One Toolkit (DIFERENCIADOR)

```typescript
// Um pacote faz TUDO:
import { scrapeUrl } from '@wenathlan/webscrape/scrape';
import { crawl } from '@wenathlan/webscrape/crawler';
import { batchScrape } from '@wenathlan/webscrape/batch';
import { serializeResult } from '@wenathlan/webscrape/serialize';
import { formatForAgent } from '@wenathlan/webscrape/agent';
import { chunkMarkdown } from '@wenathlan/webscrape/chunking';
import { generateLlmsTxt } from '@wenathlan/webscrape/llms-txt';
import { createServer } from '@wenathlan/webscrape/server';
```

**Nenhum competitor combina:**
- HTTP scraping + Browser automation
- Serialização multi-formato (incluindo Redis)
- AI agent formatting + Token estimation
- RAG chunking + LLMs.txt generation
- HTTP server REST API

### 4.3 Token Estimation (LÍDER)

```typescript
// Model-aware estimation com preços
estimateTokens(text, 'gpt-4o')      // 3.5 chars/token
estimateTokens(text, 'claude')       // 3.2 chars/token
estimateTokens(text, 'gemini')       // 3.5 chars/token
fitsInContext(text, 8000, 'gpt-4o')  // Boolean check
tokenCost(text, 'gpt-4o', 0.0025)   // Cálculo de custo
```

**Problema conhecido (AUDITORIA-DADOS.md):** Preços hardcoded em `tokens.ts` estão desatualizados (2024). Modelos listados: gpt-4o, gpt-4o-mini, gpt-4-turbo, claude-3-5-sonnet, claude-3-haiku, gemini-1.5-pro, gemini-1.5-flash.

### 4.4 RAG Chunking (LÍDER)

```typescript
// Heading-aware chunking com overlap
const chunks = chunkMarkdown(content, {
  maxTokens: 512,
  overlapTokens: 50,
  preserveCodeBlocks: true,
  includeHeadingPath: true,
});

// Output: Chunk[] com headingPath, tokenCount, index
// headingPath: ["Getting Started", "Installation", "Node.js"]
```

**Features exclusivas:**
- `splitByHeaders()` — respeita hierarquia h1-h6
- `headingPath` — caminho completo de navegação para cada chunk
- `overlapTokens` — sobreposição entre chunks para RAG
- `preserveCodeBlocks` — não quebra code blocks
- `formatChunksForRAG()` — formata chunks para ingestion

### 4.5 LLMs.txt Generation (EXCLUSIVO)

```typescript
generateLlmsTxt(results, {
  siteName: 'My Docs',
  description: 'API documentation',
  includeOptional: true,
});
// Output: # Site Name > Description ## Pages ## Documentation ## Optional
```

Nenhum competitor oferece geração de `llms.txt` — feature critical para AI discoverability de sites.

### 4.6 Multi-Format Serialization (LÍDER)

| Formato | webscrape | Scrapy | Firecrawl |
|---------|-----------|--------|-----------|
| Markdown | ✅ Custom JSDOM | ❌ | ✅ Turndown |
| XML | ✅ Custom | ✅ | ❌ |
| JSON | ✅ Structured | ✅ | ✅ |
| Redis | ✅ `JSON.SET` | ❌ | ❌ |
| Plain Text | ✅ | ❌ | ❌ |
| CSV | ❌ | ✅ | ❌ |

## 10. Conclusão

**webscrape ocupa um nicho único** como o único toolkit que combina scraping + AI formatting + RAG chunking + LLMs.txt + cross-runtime. Para use cases de "scrape → format for LLM → chunk for RAG", é superior a qualquer competitor.

**Os gaps críticos** (anti-detection, persistent queue, Docker) limitam a adoção em produção. A resolução deles — particularmente o stealth plugin que já está em `optionalDependencies` — elevaria significativamente a competitividade.

**Recomendação estratégica:** Focar nos 3 items P0 (anti-detection, persistent queue, Docker) que desbloqueiam production use, enquanto mantemos a vantagem em AI/RAG que nenhum competitor oferece de forma integrada.
