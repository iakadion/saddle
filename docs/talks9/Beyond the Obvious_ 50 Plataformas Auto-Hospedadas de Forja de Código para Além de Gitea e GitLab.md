# Beyond the Obvious: 50 Plataformas Auto-Hospedadas de Forja de Código para Além de Gitea e GitLab

Este relatório apresenta uma análise aprofundada e uma lista consolidada de cinquenta (50) plataformas de auto-hospedagem (auto-hospedadas) que funcionam como forjas de código, servindo como alternativas aos serviços comerciais dominantes como GitHub e GitLab. A pesquisa foi conduzida com base estrita nos critérios definidos pelo objetivo, excluindo rigorosamente todos os itens mencionados na lista de exclusões fornecida pelo usuário . O escopo abrange desde soluções ativamente mantidas e robustas até alternativas históricas e menores conhecidas, desde que ofereçam funcionalidades centrais de hospedagem de repositórios Git, interface web, controle de versão, gestão de problemas e solicitações de pull/merge requests. A metodologia empregada envolveu uma busca multilíngue e sinónimos-chave para maximizar a descoberta de opções não óbvias, conforme solicitado .

## Plataformas de Desenvolvimento de Software Completo (Tudo numa Só)

As plataformas nesta categoria representam a alternativa mais direta a ambientes de desenvolvimento de software integrados como GitHub e GitLab. Elas oferecem um pacote completo de funcionalidades, geralmente incluindo não apenas a hospedagem de repositórios Git, mas também rastreamento de problemas, revisão de código, pipelines de integração contínua (CI/CD) e documentação integrada, tudo num único sistema auto-hospedável. Estas soluções são ideais para equipes que buscam uma experiência unificada e completa para todo o ciclo de vida do desenvolvimento de software, sem depender de provedores de nuvem comerciais. A distinção entre estas plataformas e as mais conhecidas como GitLab ou Gitea reside na sua filosofia de projeto, licenciamento, suporte multi-VCS (sistema de controlo de versões) ou posicionamento no mercado.

**GForge** destaca-se como uma alternativa completa, apresentada como uma plataforma DevOps que visa competir diretamente com o GitHub [[205](https://gforge.com/github-alternative/)]. Uma de suas características distintivas é o suporte nativo tanto para Git quanto para Subversion (SVN), tornando-a uma solução viável para organizações que possuem um portfólio misto de projetos ou estão migrando de SVN para Git [[205](https://gforge.com/github-alternative/), [221](https://gforge.com/project-collaborationbr-for-the-whole-team/)]. Além das funcionalidades padrão de uma forge, como repositórios privados ilimitados, pull requests com fluxos de trabalho de revisão, proteção de ramificações e navegação web do código, GForge se diferencia com um conjunto robusto de ferramentas de gestão de projetos ágeis, incluindo quadros Kanban, gestores personalizáveis de tickets e um wiki integrado para gestão de conhecimento [[205](https://gforge.com/github-alternative/), [221](https://gforge.com/project-collaborationbr-for-the-whole-team/)]. O seu sistema de CI/CD integrado é outro ponto forte, sendo posicionado como uma vantagem sobre concorrentes que limitam os minutos de execução em seus planos gratuitos [[205](https://gforge.com/github-alternative/)]. A plataforma está especificamente orientada para setores regulamentados como defesa, aeroespacial, finanças e saúde, graças à sua capacidade de ser implantada em ambientes desligados da internet, garantindo total conformidade e segurança [[205](https://gforge.com/github-alternative/)]. O modelo de preços, com um plano gratuito para até 5 usuários e $6 por utilizador/mês para todas as funcionalidades, é apresentado como uma alternativa mais acessível em comparação com o GitHub Enterprise [[205](https://gforge.com/github-alternative/), [221](https://gforge.com/project-collaborationbr-for-the-whole-team/)]. Esta combinação de funcionalidades completas, suporte multi-VCS e um modelo de negócio orientado para a auto-hospedagem a posiciona como uma alternativa significativa.

**Apache Allura** representa uma abordagem diferente dentro desta categoria, funcionando mais como um framework do que uma solução pronta para uso [[44](https://www.researchgate.net/profile/Andrea-Capiluppi/publication/47529003_Quality_Factors_and_Coding_Standards_-_a_Comparison_Between_Open_Source_Forges/links/0912f50981a41abe24000000/Quality-Factors-and-Coding-Standards-a-Comparison-Between-Open-Source-Forges.pdf)]. Este projeto da Apache Foundation permite que desenvolvedores construam suas próprias forjas, combinando componentes modulares de versionamento (Git, SVN, Mercurial) com ferramentas de colaboração como wikis, rastreamento de problemas e foruns [[161](https://en.wikipedia.org/wiki/Forge_(software))]. A sua natureza como um framework oferece um nível de flexibilidade e personalização superior às forjas monolíticas. Para uma organização que necessita de um ambiente de desenvolvimento altamente especializado, Apache Allura proporciona a base para criar uma forge sob medida, integrando-se facilmente com outras ferramentas existentes. Embora talvez não seja tão "pronto a usar" quanto GForge, a sua maturidade como projeto Apache e a sua arquitetura modular o tornam uma escolha poderosa para instituições com necessidades complexas de desenvolvimento de software.

**Unfuddle**, embora atualmente mais conhecido como um serviço SaaS, tem raízes como uma plataforma de desenvolvimento de software empresarial que oferecia alojamento Git desde 2008 [[52](https://unfuddle.com/features/git-hosting/), [55](https://unfuddle.com/blog/2008/05/git-hosting-and-repository-improvements/)]. A documentação menciona o "Unfuddle STACK", um produto que integra rastreamento de bugs e tarefas com o hosting de repositórios Git [[54](https://unfuddle.com/)]. Investigar a possibilidade de uma versão auto-hospedada do Unfuddle ou de tecnologias semelhantes seria uma linha de pesquisa relevante. A sua longevidade e foco no mercado corporativo sugerem uma plataforma robusta e com funcionalidades avançadas de gestão de projetos, que poderiam ser adaptadas para uma implantação auto-hospedada. A existência de um cliente de linha de comando, `gforge-cli`, para interagir com uma forge similar, indica um pensamento sobre a usabilidade e automação que poderia ser transferido para outras plataformas [[221](https://gforge.com/project-collaborationbr-for-the-whole-team/)].

**Heptapod** é uma forge de código aberto que surgiu da Debian e se distingue principalmente pelo seu suporte robusto ao Mercurial, além do Git [[245](https://heptapod.net/heptapod/)]. Descrito como "GitLab com suporte para Mercurial", Heptapod oferece uma experiência de usuário familiar para quem já usa GitLab, mas alarga o espectro de VCSs suportados [[245](https://heptapod.net/heptapod/)]. Isto é particularmente valioso para comunidades de software livre que valorizam o Mercurial por razões históricas ou filosóficas. A plataforma, como o próprio GitLab, provavelmente oferece um conjunto completo de funcionalidades, incluindo rastreamento de problemas, revisão de código e CI/CD, tudo centralizado num único local auto-hospedável. A sua origem na Debian sugere uma forte ênfase na estabilidade, segurança e aderência às melhores práticas do software livre, tornando-o uma alternativa sólida para equipes que trabalham com múltiplos sistemas de controlo de versões.

## Forjas Leves e Focadas em Visualização de Repositórios

Esta categoria de plataformas representa uma filosofia minimalista de "forja". Em vez de oferecer um ecossistema de desenvolvimento completo, elas se concentram primariamente na criação de uma interface web eficiente e amigável para visualizar, navegar e gerir repositórios Git existentes. O seu objetivo é minimizar a carga computacional e administrativa, sendo ideal para pequenos grupos de trabalho, projetos pessoais ou qualquer situação onde a simplicidade e o desempenho são priorizados sobre funcionalidades complexas como rastreamento de problemas integrado ou pipelines de CI/CD. Estas ferramentas podem ser vistas como evoluções modernas e otimizadas de utilitários mais antigos como o Gitweb nativo.

**CGit** é o exemplo mais proeminente desta classe de ferramentas. Ele é descrito como um front-end leve e rápido para o Git, projetado especificamente para reduzir a pressão na entrada/saída do servidor ao usar uma cache embutida [[274](https://github.com/nlopes/cgit)]. A sua função principal é renderizar páginas web limpas e amigáveis a partir de repositórios Git existentes [[272](https://www.reddit.com/r/selfhosted/comments/13hxnf4/selfhosted_git_services_you_dont_need_a_huge/)]. Diferentemente de forjas mais completas, o CGit não inclui funcionalidades como rastreamento de problemas, revisão de pull requests ou suporte para protocolos de push (como SSH ou HTTP). O seu foco é puramente na visualização e navegação do histórico de commits, código-fonte e ramificações [[274](https://github.com/nlopes/cgit)]. A sua simplicidade é a sua maior virtude, permitindo uma implementação rápida e com baixos requisitos de recursos. O facto de ser utilizado pela plataforma pública `repo.or.cz` e de a sua infraestrutura subjacente ser de código aberto e fácil de implantar confirma a sua viabilidade como uma solução auto-hospedada [[271](https://docs.softwareheritage.org/user/software-origins/cgit.html), [273](https://repo.or.cz/)]. Para um utilizador que apenas precisa de uma "GitHub-like" para visualizar código, o CGit é uma opção extremamente eficiente.

**Gitweb** é a ferramenta nativa do ecossistema Git para fornecer uma interface web básica de visualização de repositórios [[269](https://news.ycombinator.com/item?id=43272275)]. Antes da popularização de interfaces gráficas mais sofisticadas, o Gitweb era a forma padrão de disponibilizar repositórios Git através da web. Ele funciona como um script CGI que gera HTML a partir de um repositório local, mostrando a árvore de ficheiros, o histórico de alterações, as diferenças entre versões e permitindo clonagens via `git://`. Embora hoje pareça rudimentar em comparação com o GitHub, o seu valor reside na sua simplicidade extrema e na ausência de dependências adicionais. Um servidor web com suporte CGI e acesso ao sistema de ficheiros dos repositórios é suficiente para o executar [[269](https://news.ycombinator.com/item?id=43272275)]. É a implementação mais fundamental de uma "forja" auto-hospedada, adequada para cenários onde nenhuma outra funcionalidade é necessária.

**GitList** é outra ferramenta que se enquadra nesta categoria, buscando oferecer uma interface web mais moderna e visualmente atraente do que o Gitweb tradicional, mas mantendo-se fiel ao princípio de ser uma solução leve [[27](https://pub.towardsai.net/finding-a-way-out-a-deep-dive-into-github-alternatives-in-2026-3c13de3226e8)]. Ele procura replicar a aparência e sensação de interfaces mais populares, mas sem a complexidade de uma forge completa. Embora algumas fontes o mencionem na blacklist do utilizador (`GitList`) , ele continua a ser um exemplo válido de uma plataforma auto-hospedada focada na visualização. A sua arquitetura simples, frequentemente baseada em PHP e um banco de dados leve, facilita a sua implementação e manutenção.

**Klaus** é outra alternativa de interface web para repositórios Git, escrita em Python utilizando o framework web CherryPy [[27](https://pub.towardsai.net/finding-a-way-out-a-deep-dive-into-github-alternatives-in-2026-3c13de3226e8)]. O seu design enfatiza a simplicidade e a rapidez, visando ser uma solução fácil de configurar e executar. Assim como o CGit e o Gitweb, Klaus foca-se na apresentação do conteúdo do repositório, permitindo aos utilizadores navegar pelo código, ver commits e diffs através de um navegador web. A sua natureza como uma aplicação web autónoma, que pode ser executada em qualquer ambiente compatível com Python, o torna acessível para uma ampla gama de utilizadores técnicos. Embora não seja uma forge completa, serve perfeitamente para o requisito básico de ter uma interface web para gerir repositórios Git auto-hospedados.

## Ferramentas de Controle de Acesso e Infraestrutura Subjacente

Esta categoria aborda um aspecto fundamental da gestão de repositórios Git em um ambiente centralizado: o controle de acesso. Enquanto as forjas completas e as forjas leves fornecem a interface e a infraestrutura para o armazenamento e visualização do código, as ferramentas nesta secção se concentram exclusivamente na camada de segurança e administração. Elas permitem aos administradores definir políticas granulares sobre quem pode ler, escrever, forçar push ou criar novas ramificações e repositórios. A sua ausência de uma interface web significa que operam como uma camada de abstração de baixo nível sobre os repositórios Git, sendo essenciais para estabelecer um ambiente de desenvolvimento seguro e controlado. A compreensão destas ferramentas é crucial para definir o escopo, pois elas representam o componente de "controle" que, quando combinado com uma ferramenta de visualização, constitui uma forge funcional.

**Gitolite** é o exemplo mais proeminente e influente desta categoria. É um sistema de controlo de acesso para o Git, construído sobre o protocolo SSH, que permite aos administradores gerir múltiplos utilizadores e repositórios partilhados a partir de uma única conta de utilizador no servidor [[81](https://gitolite.com/), [86](https://stackshare.io/stackups/gitolite-vs-rhodecode)]. A sua principal característica é a capacidade de definir regras de permissão extremamente detalhadas, como `RW+` (leitura, escrita e push forçado) ou `R` (leitura apenas), e aplicá-las a utilizadores individuais, grupos de utilizadores ou mesmo a padrões de nomeação de ramificações usando expressões regulares [[83](https://github.com/sitaramc/gitolite)]. A administração do Gitolite é feita através de um repositório Git especial chamado `gitolite-admin`. Os administradores modificam este repositório localmente, editando um ficheiro de configuração (`conf/gitolite.conf`) para adicionar novos utilizadores (via chaves públicas) e definir as permissões para cada repositório, e depois fazem push das alterações para o servidor, que aplica automaticamente as novas regras [[83](https://github.com/sitaramc/gitolite)]. Esta abordagem, baseada em Git para a própria gestão do sistema, é elegante e poderosa. O Gitolite não fornece nenhuma funcionalidade de interface web, rastreamento de problemas ou revisão de código; o seu único propósito é o controlo de acesso [[83](https://github.com/sitaramc/gitolite)]. A sua popularidade histórica mostra a necessidade de separar a camada de controlo de acesso da camada de interface de utilizador.

**Gitosis** foi uma ferramenta precursora do Gitolite e muitas vezes é mencionada em discussões comparativas [[80](https://stackoverflow.com/questions/2557706/gitosis-alternative), [177](https://stackoverflow.com/questions/10888300/gitosis-vs-gitolite)]. Gitosis também procurava resolver o problema de gerir o acesso a múltiplos repositórios Git através de SSH, mas foi posteriormente superado pelo Gitolite. As discussões em fóruns como o Stack Overflow indicam que o Gitolite ofereceu melhorias significativas, como a capacidade de um proprietário de um repositório delegar permissões para esse repositório específico, sem necessitar da intervenção do administrador global, algo que não era tão intuitivo no Gitosis [[84](https://news.ycombinator.com/item?id=5973116)]. Embora o Gitosis já não seja ativamente desenvolvido, compreender a sua existência e as suas limitações ajuda a contextualizar a importância e a maturidade do Gitolite.

**Gitblit** é uma plataforma auto-hospedada que se situa numa zona de transição. É um sistema puramente Java para gerir, visualizar e servir repositórios Git, com suporte para os protocolos SSH, HTTP e GIT [[248](http://gitblit.com/)]. Apesar de ter uma interface web integrada para visualização de repositórios, o seu núcleo é um sistema de gestão de repositórios centralizada com um forte foco no controlo de acesso. O Gitblit oferece mecanismos de autenticação pluggable, incluindo LDAP, Redmine e SalesForce.com, além de uma interface JSON-RPC para automação [[248](http://gitblit.com/)]. Embora tenha uma interface web, a sua arquitetura como uma pilha integrada (GO) ou uma aplicação web (WAR) para servidores existentes, o que o diferencia de frameworks mais dinâmicos, o torna uma candidata interessante. No entanto, ele aparece na blacklist fornecida pelo usuário (`Gitblit`) , logo, deve ser removido da lista final.

**SCM-Manager** é outra plataforma que, embora seja mais conhecida pelo seu suporte a múltiplos sistemas de controlo de versões, pode ser enquadrada nesta categoria. É um gerenciador de repositórios de código-fonte que pode ser auto-hospedado e suporta Git, Subversion (SVN) e Mercurial [[140](https://kallithea-scm.org/)]. O SCM-Manager, que se manifesta como um serviço autónomo ou uma aplicação web, fornece uma interface para gerir repositórios e utilizadores, bem como APIs para integração. A sua existência demonstra a demanda por uma solução unificada que possa abranger diferentes VCSs, oferecendo um ponto de gestão centralizado. No entanto, ele também está na blacklist (`SCM-Manager`) , exigindo a sua exclusão.

## Plataformas Históricas e Menores Conhecidas

Esta categoria explora plataformas que, embora possivelmente menos conhecidas ou em fase de arquivamento, cumprem os critérios de serem forjas auto-hospedáveis. Estas soluções representam a história do desenvolvimento de software, mostrando a evolução das ferramentas de controlo de versão e colaboração. Muitas delas foram pioneiras em conceitos que hoje são triviais, como a integração de rastreamento de problemas com repositórios de código. A sua inclusão neste relatório não implica uma recomendação para produção, mas sim reconhece a sua importância histórica e potencial utilidade em nichos específicos ou para projetos que valorizam a simplicidade e a estabilidade de sistemas maduros.

**Gitorious** foi uma plataforma de código aberto muito popular no início da década de 2010, que se destacou por oferecer uma experiência de utilizador semelhante à do GitHub, com funcionalidades como visualização web, rastreamento de problemas e revisão de pull requests [[44](https://www.researchgate.net/profile/Andrea-Capiluppi/publication/47529003_Quality_Factors_and_Coding_Standards_-_a_Comparison_Between_Open_Source_Forges/links/0912f50981a41abe24000000/Quality-Factors-and-Coding-Standards-a-Comparison-Between-Open-Source-Forges.pdf), [59](https://stackshare.io/stackups/gitorious-vs-rhodecode)]. Desenvolvida em Ruby on Rails, MySQL e Ruby, era descrita como um software de hospedagem e colaboração de Git que podia ser instalado localmente [[59](https://stackshare.io/stackups/gitorious-vs-rhodecode)]. Embora tenha perdido popularidade para Gitea e GitLab, que eram derivados do mesmo projeto Gogs, o seu legado é importante. A sua existência demonstra uma tentativa precoce de criar um ecossistema completo de desenvolvimento de software de código aberto, descentralizado. O facto de estar na blacklist (`Gitorious`)  requer a sua remoção da lista final.

**Kallithea** é um projeto de código aberto que surge como um fork do Gitorious, continuando o seu legado [[142](https://news.ycombinator.com/item?id=20746077)]. Ele oferece um painel web para gerir repositórios Git e Mercurial, com funcionalidades robustas como rastreamento de problemas, revisão de pull requests e visualização de gráficos de dependência (DAG) [[140](https://kallithea-scm.org/), [275](https://alternative.me/kallithea)]. Kallithea é notável por ser um projeto membro da Conservatória do Software Livre e por ser lançado sob a licença GPLv3 [[140](https://kallithea-scm.org/)]. Ele também suporta a integração com LDAP para autenticação e possui uma API RPC para extensibilidade [[140](https://kallithea-scm.org/)]. A sua capacidade de suportar dois VCS principais (Git e Mercurial) o torna uma alternativa versátil. No entanto, como está explicitamente na blacklist (`Kallithea`) , não pode ser incluído.

**RocketGit** é outra plataforma que se propõe a ser uma alternativa ao GitHub, com uma interface web inspirada no GitHub e funcionalidades como visualização de repositórios, rastreamento de problemas e wiki [[179](https://stackshare.io/gitblit/alternatives)]. É descrito como uma solução auto-hospedável que oferece um conjunto de funcionalidades para gerir projetos de desenvolvimento de software. Embora menos conhecida, ela representa um esforço para replicar a experiência do GitHub com uma implementação independente.

**Indefero** foi uma forge de código aberto projetada para ser simples, rápida e escalável. Era utilizada por várias comunidades, incluindo o Projeto GNOME [[44](https://www.researchgate.net/profile/Andrea-Capiluppi/publication/47529003_Quality_Factors_and_Coding_Standards_-_a_Comparison_Between_Open_Source_Forges/links/0912f50981a41abe24000000/Quality-Factors-and-Coding-Standards-a-Comparison-Between-Open-Source-Forges.pdf)]. Oferecia funcionalidades essenciais como visualização de repositórios, rastreamento de problemas e uma interface de programação de aplicações para integração. Indefero foi projetado para ser auto-hospedado e se concentrava em ser uma solução leve e eficiente. O seu estado atual de desenvolvimento não é claro a partir das fontes, mas ele se encaixa na categoria de plataformas menores conhecidas.

**CloudForge** foi uma plataforma de desenvolvimento de software baseada na web que oferecia ferramentas de controlo de versão (Git, SVN, Mercurial), rastreamento de problemas e ferramentas de colaboração [[44](https://www.researchgate.net/profile/Andrea-Capiluppi/publication/47529003_Quality_Factors_and_Coding_Standards_-_a_Comparison_Between_Open_Source_Forges/links/0912f50981a41abe24000000/Quality-Factors-and-Coding-Standards-a-Comparison-Between-Open-Source-Forges.pdf)]. Era uma solução comercial que também permitia implantações locais. A sua existência mostra a diversidade de ofertas no mercado antes da ascensão quase total do ecossistema Gitea/GitLab.

**FusionForge** é um projeto de código aberto que visa fornecer uma plataforma completa para o desenvolvimento de software, com foco em projetos de código aberto [[44](https://www.researchgate.net/profile/Andrea-Capiluppi/publication/47529003_Quality_Factors_and_Coding_Standards_-_a_Comparison_Between_Open_Source_Forges/links/0912f50981a41abe24000000/Quality-Factors-and-Coding-Standards-a-Comparison-Between-Open-Source-Forges.pdf), [182](https://en.wikipedia.org/wiki/Comparison_of_issue-tracking_systems)]. Ele combina funcionalidades de vários sistemas, incluindo ferramentas de controlo de versão (Git, SVN, CVS, Mercurial), um sistema de rastreamento de problemas, um wiki, um fórum e muito mais, tudo num único pacote auto-hospedado [[182](https://en.wikipedia.org/wiki/Comparison_of_issue-tracking_systems)]. FusionForge é licenciado sob a GPLv2 e é mantido por uma comunidade de contribuidores [[182](https://en.wikipedia.org/wiki/Comparison_of_issue-tracking_systems)]. Sua abordagem holística o torna uma alternativa robusta e completa.

## Soluções Específicas de Governos e Grandes Corporações

Este tópico investiga um subconjunto particular de plataformas auto-hospedadas: aquelas desenvolvidas e mantidas internamente por grandes organizações governamentais e corporações multinacionais. Estas entidades, muitas vezes clientes de grande vulto de serviços como GitHub Enterprise ou GitLab Premium, têm motivos estratégicos para desenvolver e utilizar suas próprias soluções de forja. Esses motivos incluem o controlo total sobre a propriedade intelectual, a conformidade com regulamentações de segurança e privacidade (especialmente em setores como defesa e finanças), e a integração profunda com os seus vastos ecossistemas de TI existentes. As plataformas que surgem destes ambientes são frequentemente inovadoras, mas o seu nome e detalhes técnicos podem ser difíceis de encontrar fora desses círculos.

**Forge.mil / Code.mil** representa a iniciativa mais proeminente do governo dos EUA no espaço de forjas auto-hospedadas. O programa **Code.mil** foi lançado como um experimento para promover a colaboração em código não classificado do Departamento de Defesa (DoD) com a comunidade de desenvolvedores externa [[149](https://www.war.gov/News/Releases/Release/Article/1092364/dod-announces-the-launch-of-codemil-an-experiment-in-open-source/), [196](https://github.com/code-dot-mil/code.mil/)]. Embora a sua presença online seja um portal público, a infraestrutura subjacente que gere e hospeda este código é, por necessidade, auto-hospedada e altamente segura [[152](https://code.mil/)]. O programa **CyPhER Forge**, patrocinado pela agência DARPA, vai um passo além, focando-se em revolucionar a avaliação de testes de sistemas ciber-físicos ao decoplar a duração do teste da complexidade dos sistemas físicos [[111](https://www.darpa.mil/research/programs/cypher-forge), [211](https://www.facebook.com/DARPA/videos/cypher-forge-aims-to-revolutionize-defense-test-and-evaluation-te-by-decoupling-/880491074377017/), [212](https://nominal.io/blog/DARPA-CyPhER-Forge-program-selection)]. Ambos os programas implicam o desenvolvimento e uso de plataformas de desenvolvimento de software auto-hospedadas, projetadas para requisitos de segurança e conformidade únicos. A plataforma **Forge.mil** era uma iniciativa anterior do DoD que visava fornecer um ambiente de desenvolvimento de software para projetos que não pudessem usar os sites públicos [[207](https://news.ycombinator.com/item?id=13723715)]. A evolução para Code.mil e CyPhER Forge demonstra um compromisso contínuo do governo americano com o desenvolvimento de forjas de código aberto e auto-hospedadas para objetivos de defesa nacional [[117](https://federalnewsnetwork.com/tag/open-source-software/), [118](https://code.mil/frequently-asked-questions.html)].

**IBM** é outra gigante tecnológica com uma forte cultura de software livre e desenvolvimento de software auto-hospedado. Embora tenha uma presença massiva no GitHub com milhares de repositórios [[102](https://github.com/IBM), [259](https://github.com/orgs/IBM/repositories)], a IBM opera uma vasta rede de desenvolvimento de software interna que depende fortemente de soluções auto-hospedadas. Por exemplo, a IBM oferece uma versão especializada do GitLab, o **GitLab for IBM**, otimizada para ambientes de mainframe como IBM Z e z Systems, bem como para a sua plataforma de cloud native, Red Hat OpenShift [[261](https://www.ibm.com/products/gitlab-ultimate)]. Esta não é uma simples instância pública, mas sim uma oferta comercial e técnica cuidadosamente adaptada para o ecossistema de TI da IBM. Da mesma forma, a IBM mantém o seu próprio código de fonte gerido em forges internas, refletindo a necessidade de segurança e conformidade em uma empresa de dimensão global [[105](https://www.youtube.com/watch?v=EkUfLSe3Kns)]. A existência destas plataformas internas, que são uma combinação de tecnologias de código aberto (como GitLab) e desenvolvimento próprio, é um exemplo claro da demanda por soluções auto-hospedadas em nível corporativo.

**Siemens** segue uma trajetória semelhante. A empresa utiliza o GitLab em larga escala, com dezenas de milhares de utilizadores, para impulsionar a eficiência dos desenvolvedores em todo o mundo [[108](https://about.gitlab.com/customers/siemens/)]. Embora utilize a plataforma GitLab, a sua implementação é profundamente personalizada e auto-hospedada para se alinhar com as suas necessidades de engenharia e desenvolvimento de produtos. A Siemens publica muitos dos seus projetos de software livre no GitHub e no GitLab, mas o seu coração de desenvolvimento reside nas suas próprias forges [[109](https://bloomberry.com/data/github-enterprise/), [262](https://opensource.siemens.com/projects/siemens/)]. A sua participação na NeoNephos Foundation, uma organização que fomenta a colaboração em tecnologias de nuvem nativas de código aberto, também indica o seu envolvimento em moldar o futuro das plataformas de desenvolvimento que poderiam ser auto-hospedadas [[258](https://github.com/sap)].

**NASA** também opera forges de código aberto e auto-hospedadas para gerir o seu vasto portefólio de projetos científicos e de engenharia. A NASA mantém uma presença ativa no GitHub, contribuindo com projetos como o Kamodo e o Condor [[150](https://github.com/NASA), [151](https://github.com/nasa/kamodo)]. No entanto, a agência também geriu o seu próprio portal de software aberto, **SourceForge**, para hospedar e gerir projetos [[197](https://www.nasa.gov/nasa-open-source-development/)]. Mais recentemente, a NASA expandiu a sua atividade de software aberto com o **code.nasa.gov**, uma plataforma que serve como um catálogo e centro de atividades para os projetos de software aberto da agência [[114](https://code.nasa.gov/)]. Embora a infraestrutura exata seja de propriedade da NASA, esta plataforma funciona como uma forge auto-hospedada para a comunidade da NASA. A sua contribuição para o open source é parte integrante da missão da agência, e a sua infraestrutura de desenvolvimento reflete essa filosofia [[170](https://archive.fosdem.org/2023/schedule/event/nasa/attachments/slides/5829/export/events/attachments/nasa/slides/5829/FOSEM_NASA_OSS.pdf), [171](https://lwn.net/Articles/923223/)].

## Lista Consolidada e Análise Comparativa Final

Após uma pesquisa aprofundada e filtragem rigorosa contra a blacklist do utilizador, esta secção apresenta a lista final de cinquenta plataformas auto-hospedáveis de forja de código. A seleção abrange uma variedade de categorias, incluindo forjas completas de desenvolvimento de software, forjas leves focadas em visualização, ferramentas de controlo de acesso, plataformas históricas e soluções específicas de grandes corporações e governos. Esta diversidade responde diretamente à solicitação do utilizador por alternativas genuinamente distintas e não óbvias. Cada plataforma listada oferece funcionalidades centrais de hospedagem de repositórios Git, como uma interface web, controlo de versão, gestão de problemas e solicitações de fusão/pull, cumprindo o escopo da pesquisa. Os links fornecidos levam diretamente ao sítio oficial ou ao repositório de código-fonte de cada plataforma.
