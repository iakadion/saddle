O que é o OpenCode na prática
OpenCode não é uma lib de front. É um CLI híbrido Go + Bun distribuído como binário.

Repo oficial: anomalyco/opencode (antigo sst/opencode). Monorepo Bun + Hono + OpenTUI.
OpenTUI é o framework da TUI, core em Zig com binding pra TS via C ABI: @opentui/core, @opentui/react.

O pacote opencode-ai do NPM é só um wrapper que baixa o binário certo pra sua plataforma e coloca em ~/.opencode/bin ou ~/.cache/opencode.

Bash
npm i -g opencode-ai@latest # baixa binário opencode-<platform>
opencode # inicia
3 pacotes que importam
1. opencode-ai - O CLI. Não é ESM. bin: { opencode:./bin/opencode }. Se você tentar importar via ESM.sh / Skypack / jsDelivr, vai vir shim vazio. Ele não serve pra browser.

2. @opencode-ai/sdk - O cliente JS/TS type-safe do servidor. Esse SIM funciona via ESM.sh, jsDelivr, UNPKG, Skypack.

JavaScript
import { createOpencode } from "@opencode-ai/sdk"
const { client, server } = await createOpencode() // sobe servidor + cliente
// server.url = http://127.0.0.1:4096
Instalação oficial:

### O que acontece quando você abre uma aba

> Mental model correto: **TUI é só um cliente. O servidor é o core.**

1. Você roda `opencode` -> entry `packages/opencode/src/cli/index.ts` -> comando `tui`
2. `cli/cmd/tui/worker.ts:36` chama `Server.listen()` - **spawna um HTTP server Hono em Bun**
3. Quando você roda `opencode` ele inicia TUI e servidor. Onde a TUI é o cliente que fala com o servidor【8054225820145044620†L77-L80】
4. Se você não passa `--port`, a TUI aloca porta aleatória【8054225820145044620†L84-L86】. Se roda `opencode serve` ou `opencode web`, default é `4096`【8054225820145044620†L45-L48】

Config do server:

    "hostname": "0.0.0.0",
    "mdns": true

5. Server expõe OpenAPI 3.1 em `/doc` -> `http://localhost:4096/doc`【8054225820145044620†L89-L93】
6. Endpoints principais: `/global/health`, `/global/event` (SSE stream), `/project`, `/session`, `/tui`
7. TUI conecta via SDK (`createOpencodeClient({ baseUrl: "http://localhost:4096" })`)【4927272958616767605†L48-L53】 usando SSE pra streaming.
8. Sessão criada = pasta em `~/.local/share/opencode` ou `.opencode/` com arquivos `JSONL` append-only. Toda tool call, message, file edit vira evento nesse JSONL.

### Como funciona o SDK na prática

`createOpencode()` faz 3 coisas:
- Spawn do processo `opencode serve` com port/hostname que você passar (default `127.0.0.1:4096`)【4927272958616767605†L25-L32】
- Aguarda health check
- Retorna `client` tipado (gerado do OpenAPI) + `server` com `.url` e `.close()`

```js
const opencode = await createOpencode({
  hostname: "127.0.0.1",
  port: 4096,
  config: { model: "anthropic/claude-3-5-sonnet-20241022" }
})
console.log(`Server running at ${opencode.server.url}`)
opencode.server.close()
```【4927272958616767605†L35-L46】

Se já tem server rodando, usa `createOpencodeClient({ baseUrl: "http://localhost:4096" })`

## 0. Realidade hoje
`opencode-ai` do NPM é binário Go+Bun compilado. Ele ABRE porta (default 4096 ou random) com Hono server + OpenAPI 3.1 + SSE.
No browser você NÃO pode fazer `bind()` de porta nem `spawn()` de binário. Então 100% inline só tem 3 caminhos reais.

Raciocinando nos seus fatos - V4
Fato 1: No Linux tudo é arquivo
Você está certo. No kernel tudo é inode + dentry + file_operations. Processo em /proc, memória em /dev/shm, device em /dev. Se implementa read/write/mmap, É arquivo. VFS abstrai ext4, tmpfs, proc. Prova que storage e RAM são mesma coisa, só muda o backing.

Fato 2: Formatos, mimetypes, magic bytes
Extensão é UX. Verdade é magic byte nos primeiros bytes: ELF 7F 45 4C 46, PE 4D 5A, PNG 89 50 4E 47, ZIP 50 4B. libmagic lê isso pra decodificar. Repo guarda bytes estáticos com magic, browser faz fetch e decodifica via loader.

Fato 3: Encoding / Decoding
Arquivo no disco é encode estático. Loader lê magic, escolhe parser, mapeia pra RAM, executa. Igual Windows: arquivos ficam estáticos, na hora de rodar busca paginação, dump de memória, decodifica PE -> executa.

Fato 4: Sandbox tem VFS virtual - Docker, K8s
